## What this is
**TGDG Overwatch**: a small desktop app that pins itself to the right edge of the screen and stays there — a docked panel for dispatch tools (starting with the zip/tech/availability console), alongside whatever browser the dispatcher has open (Housecall Pro today, other tools later). Overwatch is a *shell*, not one hard-wired tool — the zip/tech/availability console is the first thing it loads, not the whole product.

Team: lead full-stack dev + a UI/UX specialist (persona, brought in for panel/shell design specifically) + a junior dev. Both the lead dev and UX talk directly to the user as a 10+ year full-stack dev who's rusty and re-ramping — not a beginner, just out of practice.

## Architecture decision: desktop app, not a browser extension (2026-10-03)
Started as three separate browser extensions (Chrome/Edge via `chrome.sidePanel`, Firefox via `sidebar_action`), with Safari out of scope since it has no sidebar API at all. That approach is **retired**. Instead, Overwatch is now a small **Electron app**:
- Opens its own window, pinned to the right edge of the primary display, on launch
- Works identically regardless of which browser is open next to it — Chrome, Edge, Firefox, Safari, or none of them — because it doesn't depend on any browser's extension APIs
- One codebase instead of three manifest variants
- Can stay visible even when no browser window is focused (not tied to being "inside" a specific browser's chrome)

Trade-off, stated plainly: it's no longer "lives in the browser's toolbar" — it's a separate small app the dispatcher launches once and leaves pinned to the screen edge. For an internal tool, that's considered a fair trade for genuine any-browser support and a single codebase.

## Architecture
- `src/main.js` — Electron main process: creates the docked `BrowserWindow`, positions it against the screen's work area (excludes OS menu bar/taskbar), handles a tiny JSON-file-backed storage via IPC
- `src/preload.js` — exposes that storage to the renderer as `window.overwatch`, with context isolation on and no Node integration in the renderer (standard Electron security practice)
- `src/sidepanel.html/.css/.js` — the panel UI: icon rail across the top, a settings gear for overriding the active tool's URL, an iframe showing the active tool
- `src/tools.js` — the tool registry. Each tool is just `{ id, name, defaultUrl, glyph }` loaded in an iframe; adding a new docked tool means adding one entry here, not rebuilding anything
- The existing dispatcher console backend (Next.js + Prisma + Neon) is the first tool's content, loaded by URL — that work isn't thrown away, it's just one iframe's worth of content now instead of the whole product

## Calendar events as blocked time (built 2026-10-07; NOT yet seen against real HCP event data)
- **Decisions (user, 2026-10-07):** EVERY event blocks time and EVERY event is shown, because the dispatcher must see what affects a tech's availability, including a new dispatcher who needs to visually check the schedule. So the event's short title (60 characters max) is stored and shown on screen, not hidden.
- **Built:** sync reads HCP `GET /events` (tries plain dates then full timestamps; stops if HCP ignores the dates), stores rows with `kind = "event"` and `label` (two new columns, migration `appointment-kind-label`), `hcpJobId = "event:<id>"`. Per-kind cleanup; job and event syncs never delete each other's rows; zero events returned never wipes. An events failure never stops the job sync. Screen: steel-blue cross-hatch (own color AND pattern), title on the bar, a written line per event under the bar, legend entry, events-only days still shown, an event is never a "nearby call" for stacking.
- **Reader is defensive because the real shape is unverified:** assignees only from assignee-style fields; never uses a repeat-series end date; all-day events given as plain dates are skipped; unreadable events are listed in the sync output (`events.unreadable`: id ending, reason, field NAMES only). First real step: run the sync as a dry run and read the `events` block. If `unreadable` is not empty or `events.error` appears, send it and the reader gets fixed from real field names.
- **Real event shape (from the user's probe, 2026-10-08):** `id` ("evt_..."), `name` (title), `note`, `tags[]`, `recurrence_rule` (null in the sample), `address{}` (all null), `assigned_employees[]` (full person objects with permissions; the person id is `.id`), `schedule{start_time, end_time, time_zone}` (UTC with Z), `all_day` (bool), `created_at`, `updated_at`. The reader matches this exactly (44 reader/sync checks, including a faithful copy of this shape).
- **HCP ignores the date range on `/events`.** A request for one day returned 100 events spanning Aug 28 to Oct 16, newest-created first (page_size 100 honored). So the sync must read through the pages and keep only what overlaps the window. The probe did not print `total_items`, so the total is unknown; the dry-run sync reports `events.fetched` (the total read). If that is large, plan: stop paging once a page's newest `created_at` is older than a safe cutoff (valid only while the list stays newest-created-first, which the first page suggested), or cache and read incrementally. Each event carries full person objects, so pages are heavy (about a megabyte or more).
- **No live updates for events.** HCP's webhooks cover jobs and appointments, not calendar events, so events are only as fresh as the last sync. For the future multi-appointment fix, HCP does send appointment webhooks: `job.appointment.scheduled`, `.rescheduled`, `.appointment_discarded`, `.appointment_pros_assigned`, `.appointment_pros_unassigned`.
- **Observations:** Drayton's product pickup is Thu Oct 8, 8:00-9:00 AM, shared with Justin Banks. Many events are 6:45-8:00 AM team meetings, before business hours, so they are clipped away and won't clutter the day. One person id (`pro_8aee5...`) appears on several team events but is not in our employee list (probably a former employee); the sync reports unknown people and ignores them.
- **Known gaps:** whether `recurrence_rule` is ever non-null (the first page looked like each occurrence is its own event); whether `all_day` events still carry real start/end times (the reader uses the times if present); the diagnose report does not cover events yet.

- **Webhook signature scheme** is unconfirmed; the verifier accepts any standard HMAC-SHA256 construction and logs which one matched. Pin it to that one once seen. Replay protection (timestamp tolerance) is not yet enforced.

- **"End of week" meaning:** built as days 3-7 (a rolling week), so on a Thursday it runs Saturday through Wednesday. If dispatch means "through Friday/Saturday of this calendar week", that's a small change.
- **Business days:** the engine treats every day as open during business hours, Sundays included. HCP shows Saturday jobs exist. Confirm which days the business is open (and any different weekend hours) before trusting weekend slots.
- **How far a human can look:** 30 days ahead (the sync mirrors exactly that far, so every selectable day has real data). Further out the console tells the dispatcher to check HCP directly, instead of showing a falsely open day.


- **The dispatch console itself still has no login.** The admin login exists and could protect the console too (not done). Before the console sits on a public URL with real data, it needs one.

- **Travel time between calls is not modeled.** A start time flush against a call assumes zero driving between jobs. The screen shows "about N min away" for each neighbor, but doesn't reserve that time. Decide with dispatch whether to add a buffer (and how big).
- **Is 10 minutes the right meaning of "nearby"?** In the Little Rock area 72201 to 72202 (3 min) and 72205 (10 min) count as near; 72204 (11 min) does not. One constant in `src/lib/zip-distance.ts`.
- **Zips outside Arkansas** have unknown distance (only exact same-zip counts as near). Add centers if the service area ever crosses the state line.

- **Known gap, confirmed by test (2026-10-06): multi-day / multi-appointment jobs.** HCP lets one job have several appointments, each with its own date and hours (installs are the classic case). The sync reads only the job-level schedule, and HCP's date filter goes by the job's FIRST start, so (a) a job that began before the sync window is never fetched and (b) a visit that is only an extra appointment never blocks time. `node scripts/hcp-diagnose.mjs "<name>" <date>` shows which applies to real data. Fix planned after that report: read each job's appointments (and who is dispatched on each), look back far enough to catch jobs already under way, and keep only visits overlapping the window. Cost to weigh: one extra HCP request per job per sync unless the job list already embeds the appointments (the diagnose report says how many it embeds).
- **Estimates and calendar events are not read at all.** In HCP an Estimate (a sales or measuring visit) and an Event (time off, a meeting) are different from a Job, so they never block time here. Possible cause of a tech looking free; the diagnose report flags it when it finds no job for that person and day.

- **Archived jobs.** HCP archives finished jobs (hides them). For an archived job, `GET /jobs/{id}/appointments` and `GET /jobs/{id}` answer `400 {"error":{"message":"Archived job"}}`, while the job LIST still returns it and (as far as the sample showed) does not mark it. Handled so far: the diagnose report flags and skips archived jobs instead of failing, and the look-back skips finished jobs; for live updates an archived job is treated as gone so its booking clears. Not known yet: whether an archived job can sit in the FORWARD window and look falsely booked in the console; the report prints any "archive" field the list carries so we can see.
- **Diagnose a day that is still ahead.** Past days are over (and mostly archived); to test why a tech looks free, run the report for today or a future day where HCP shows a job.

## Weekend recap (built 2026-10-20)
- WHY: the office is not at the computer on weeknights and weekends, and the user does not want to miss estimates or go-backs. Techs cannot turn a job into an estimate, so what else is needed is in their notes. A Monday-morning page reads those notes for the weekend.
- WINDOW: Friday 6:00 PM to Sunday 10:00 PM, business time zone (correct across daylight-saving changes). `/weekend` shows the latest weekend that has started (going on now, or the one that just ended); Earlier/Later weekend buttons go back up to 8; `?back=N` and `?fresh=1` on /api/weekend-recap.
- WHAT IT SHOWS: every non-canceled job with a start, finish, or scheduled time in the window: job type and number, tech names, how it ended (finished after N min / never finished / never started), the notes IN FULL (up to 8 notes, 1000 characters each; Job Watch cuts them shorter), and a Go to job link. NO customer name, phone, email, address or job description (only what a tech typed in the notes, which can contain a gate code, so it sits behind the console sign-in like the rest; JOB_WATCH_SHOW_NOTES=off hides notes here too).
- FLAGS (listed first, with a chip): (1) notes mention a flagged word (default list in DEFAULT_WORDS: part(s), order, need(s), return, go back, come back, call back, quote, estimate, waiting, on hold, schedule, unable, couldn't, ...; replace with WEEKEND_RECAP_WORDS, comma separated); the matched words are highlighted. (2) a finished job with NO notes. (3) never finished (in progress more than 6 h, or its time passed and it was never started). A flag is a hint, not a verdict ("no parts needed" also flags). Whole words only ('apartment' does not match 'part').
- MARK REVIEWED: per browser (localStorage overwatch.recap.reviewed, keyed weekend-start|job id, 90 days). NOT shared between people or computers. Reviewed jobs dim and sink to the bottom; the count of "need a look" drops. Making it shared would need a small database table (a migration); the user has not asked.
- WIRING: src/lib/weekend-recap.ts (pure engine: window, notes, words, evaluation, cached read; imports only types), weekend-recap-live.ts (real HCP + settings, shares Job Watch's install words and link template), src/app/api/weekend-recap/route.ts (always 200; failure is {ok:false,error}; 5-minute cache per weekend; at most 10 pages of 100 jobs and 25 job-record reads for missing notes), src/app/weekend/page.tsx, src/app/SiteNav.tsx (a Dispatch / Estimates / Weekend recap link row on the website pages, hidden inside the desktop panel which has its own tabs). The desktop panel gets a new "Weekend" tab (src/tools.js id "weekend"); its tests (tests/shell) were updated for the fifth tool. job-watch.ts now exports techNames and employeeNames (no behavior change).
- HCP LIMIT: the job list is filtered by a job's FIRST scheduled start (known gap), so the read starts a day before the window; a multi-day job that began earlier and was worked on the weekend may not appear.
- TESTS: unit/weekend-recap.test.mts (72 checks in 4 time zones: window incl. both daylight-saving weekends, words/highlighting, notes, flags, reading/caching/failure), server/weekend-recap-route.test.cjs (25, real route + real HCP client against a stand-in, time pinned to Mon Oct 19 2026 9 AM), ui/weekend-page.test.cjs (42). 17 deliberate breaks were all caught (one survived at first: a missing word-start check; a test was added).
- NOT VERIFIED ON REAL DATA YET: how the flags feel on a real weekend (too noisy or too quiet; tune WEEKEND_RECAP_WORDS), and that weekend job lists contain the notes the way the weekday ones do (they should: same job list).
- LATER (offered, not built): a Monday 8 AM phone alert "Weekend recap: N jobs, M need a look" through the existing alert pipeline; shared reviewed marks; an after-hours alert schedule.
