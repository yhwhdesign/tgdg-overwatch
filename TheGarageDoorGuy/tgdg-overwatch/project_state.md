# TGDG Overwatch — Project State

_Last updated: 2026-10-04_

## What this is
**TGDG Overwatch**: a small desktop app that pins itself to the right edge of the screen and stays there — a docked panel for dispatch tools (starting with the zip/tech/availability console), alongside whatever browser the dispatcher has open (Housecall Pro today, other tools later). Overwatch is a *shell*, not one hard-wired tool — the zip/tech/availability console is the first thing it loads, not the whole product.

Team: lead full-stack dev + a UI/UX specialist (persona, brought in for panel/shell design specifically) + a junior dev. Both the lead dev and UX talk directly to the user as a 10+ year full-stack dev who's rusty and re-ramping — not a beginner, just out of practice.

## Architecture decision: desktop app, not a browser extension (2026-10-03)
Started as three separate browser extensions (Chrome/Edge via `chrome.sidePanel`, Firefox via `sidebar_action`), with Safari out of scope since it has no sidebar API at all. That approach is **retired**. Instead, Overwatch is now a small **Electron app**:
- Opens its own window, pinned to the right edge of the primary display, on launch
- Works identically regardless of which browser is open next to it — Chrome, Edge, Firefox, Safari, or none of them — because it doesn't depend on any browser's extension APIs
- One codebase instead of three manifest variants
- Can stay visible even when no browser window is focused (not tied to being "inside" a specific browser's chrome)

Trade-off, stated plainly: it's no longer "lives in the browser's toolbar" — it's a separate small app the dispatcher launches once and leaves pinned to the screen edge. For an internal tool, that's considered a fair trade for genuine any-browser support and a single codebase.

## Zero-cost plan (verified via research)
- Electron itself: free, MIT-licensed, no platform fee of any kind.
- Distribution: unsigned builds via `electron-builder`, genuinely $0. On macOS (post-Sequoia), opening an unsigned app requires System Settings → Privacy & Security → "Open Anyway" once per machine (Control-click bypass no longer works as of Sequoia) — a one-time step, not a recurring cost. Windows SmartScreen has an equivalent one-time "Run anyway" click.
- Hosting: **CORRECTION (2026-10-04):** this line previously assumed Vercel's free Hobby plan. Vercel restricts Hobby to non-commercial personal use only, and this is a business tool, so Vercel would need the Pro plan (about $20/month). Production hosting is now an open decision, see Open questions. Neon (Postgres) is already cloud-hosted; its free-plan terms have not been re-checked yet.
- **The only real dollar figure anywhere in this plan:** a signed/notarized macOS build via the Apple Developer Program would cost $99/year — not part of the current plan, only relevant if this ever needs to be distributed more broadly without the one-time Gatekeeper click.

## Architecture
- `src/main.js` — Electron main process: creates the docked `BrowserWindow`, positions it against the screen's work area (excludes OS menu bar/taskbar), handles a tiny JSON-file-backed storage via IPC
- `src/preload.js` — exposes that storage to the renderer as `window.overwatch`, with context isolation on and no Node integration in the renderer (standard Electron security practice)
- `src/sidepanel.html/.css/.js` — the panel UI: icon rail across the top, a settings gear for overriding the active tool's URL, an iframe showing the active tool
- `src/tools.js` — the tool registry. Each tool is just `{ id, name, defaultUrl, glyph }` loaded in an iframe; adding a new docked tool means adding one entry here, not rebuilding anything
- The existing dispatcher console backend (Next.js + Prisma + Neon) is the first tool's content, loaded by URL — that work isn't thrown away, it's just one iframe's worth of content now instead of the whole product

## Repo
Single repo: **`tgdg-overwatch`**, structured as a monorepo:
- Repo root — the Electron shell (`src/main.js`, `src/preload.js`, panel UI)
- `tools/dispatch-console/` — the first docked tool, a standalone Next.js app with its own `package.json`, run independently (`npm run dev` inside that folder) and deployed separately later (e.g. Vercel, with its "Root Directory" set to `tools/dispatch-console`)

## Roadmap notes (captured 2026-10-07; none of this is built yet)

### Overwatch shell (the docked panel)
- **Docking, as it works today:** on launch the window is placed against the right edge of the primary display, full height, 380 px wide, always on top. It works the same next to any browser (Chrome, Edge, Firefox, Safari) because it is its own app, not something running inside a browser. **Limits to know:** it is placed once at launch (the user can drag it away, and it is not re-snapped if the monitor changes or remembered between launches), and it cannot reserve screen space, so a maximized browser sits underneath it. The practical workflow is to snap the browser to the left part of the screen (macOS/Windows window snapping). Planned: re-dock on launch and when displays change, remember the last position, choose which monitor, optional narrow/wide toggle.
- **Tabs:** the icon rail already exists (`src/tools.js` registry). Add an **Admin** tab. When there are too many tabs for the width, the extras go into a **burger (hamburger) menu**.
- **Technical catch for an Admin tab inside the panel:** tools load in an iframe, and the admin sign-in cookie is `SameSite=Strict`, so it will not stick inside an iframe on the panel's local page (it counts as a different site). Plan: load each tool in its own top-level web view (Electron `WebContentsView`) instead of an iframe, which makes the cookie first-party and also gives each tool its own session. Until then, open `/admin` in a normal browser tab.

### Estimate Tracker (tab)
- Pull ALL estimates from HCP, new and old, and track them (status, age, amounts as needed). The HCP API does expose estimates; the response shape has NOT been probed yet (needs a read-only probe like the jobs one).
- **Emails to the team** (recipients chosen in the Admin panel) when an estimate is updated, finished, or has gone old. "Old" needs a threshold (decide: how many days, per status).
- Needs: (1) something that runs on a schedule even when the app is closed, since "old" is a time-based check; (2) a way to send email for free (options to evaluate then: SMTP through the existing DreamHost mailbox, or a free-tier email service; limits not yet verified); (3) a decision on what customer detail an estimate record keeps. So far we deliberately store no customer names or addresses, and emails and an estimate list will want at least a customer name and amount, so decide on purpose. HCP may send webhooks for estimate changes (event list not checked yet).

### Job Watch (tab)
- Checks about every 10 minutes (HCP webhooks could make this near-instant; polling is the fallback). Shows jobs as they are **completed**, and alerts when a tech (or techs) has been **on a job longer than a set time**.
- The data exists: each job carries `work_timestamps` (on_my_way_at, started_at, completed_at) in the real HCP data. "On a job too long" = now minus started_at while completed_at is empty.
- Thresholds set in the Admin panel; they will probably need to differ by job type (an install legitimately runs all day, a repair should not).
- **Caveat:** it only works when techs tap Start / Complete in the HCP app. No taps, no data.
- Alerts: shown in the tab; desktop notifications (free, but only while Overwatch is open); optional email (shares the email piece above). Alerts that must fire with the app closed need the same always-running scheduler as the Estimate Tracker.

### Inventory
- Last. Build at the very end.

- A **scheduler** that runs without the app open, and the hosting that goes with it: the Netlify-vs-VPS decision (under Open questions) now matters more, since a VPS makes "run every 10 minutes" trivial, while free serverless hosting needs a scheduled-function feature whose free limits are unverified.
- **Email sending**, **Admin-panel settings** for recipients and thresholds, and a **login on the dispatch console itself** (it has none today).
- Suggested order: finish the accuracy fixes in progress (the diagnose report, multi-day jobs) > shell upgrades (Admin tab, burger menu, re-dock) > Job Watch (data is known; desktop notifications need no email) > Estimate Tracker (needs the estimate probe and email) > Inventory.

Watch-outs: each production deploy costs 15 of 300 monthly credits (branch/preview deploys are free), and the free plan can't buy extra credits.

- **No authentication on the dispatch console yet.** Anyone with the URL can load the console and call its API routes. Harmless with seed data, but once real HCP data is in the database this exposes real technician names and schedules, on any host and on the ngrok tunnel too. Needs access control (a login, or at minimum an IP allowlist / ngrok traffic policy) before real data sits behind a public URL.

- **How busy should a tech look?** HCP schedules jobs as 2-hour blocks, but dispatch's rule is a 1-hour real job inside a 2-hour customer window. Stored data keeps HCP's real blocks; the choice (count the full HCP block as busy, or only the first hour) belongs in the availability read path. Decide with dispatch before trusting same-day numbers.
- **Who is dispatched** is decided only on the Admin screen by classification (R/C/H). The `active` flag no longer gates the console.
- **Zip codes are not assigned to technicians** (decided 2026-10-06). Anyone marked on the Admin screen is offered in every zip; the customer's zip is only used to find nearby calls.
- **Multi-visit jobs:** v1 reads each job's primary schedule + assigned employees. Jobs with several appointments (`/jobs/{id}/appointments`) may need an extra fetch; webhooks for appointment changes already trigger a full re-read of the job.
- **Webhook signature scheme** is unconfirmed; the verifier accepts any standard HMAC-SHA256 construction and logs which one matched. Pin it to that one once seen. Replay protection (timestamp tolerance) is not yet enforced.

- **"End of week" meaning:** built as days 3-7 (a rolling week), so on a Thursday it runs Saturday through Wednesday. If dispatch means "through Friday/Saturday of this calendar week", that's a small change.
- **Business days:** the engine treats every day as open during business hours, Sundays included. HCP shows Saturday jobs exist. Confirm which days the business is open (and any different weekend hours) before trusting weekend slots.
- **How far a human can look:** 30 days ahead (the sync mirrors exactly that far, so every selectable day has real data). Further out the console tells the dispatcher to check HCP directly, instead of showing a falsely open day.


- **The dispatch console itself still has no login.** The admin login exists and could protect the console too (not done). Before the console sits on a public URL with real data, it needs one.

- **Travel time between calls is not modeled.** A start time flush against a call assumes zero driving between jobs. The screen shows "about N min away" for each neighbor, but doesn't reserve that time. Decide with dispatch whether to add a buffer (and how big).
- **Is 10 minutes the right meaning of "nearby"?** In the Little Rock area 72201 to 72202 (3 min) and 72205 (10 min) count as near; 72204 (11 min) does not. One constant in `src/lib/zip-distance.ts`.
- **Zips outside Arkansas** have unknown distance (only exact same-zip counts as near). Add centers if the service area ever crosses the state line.

- **Known gap, confirmed by test (2026-10-06): multi-day / multi-appointment jobs.** HCP lets one job have several appointments, each with its own date and hours (installs are the classic case). The sync reads only the job-level schedule, and HCP's date filter goes by the job's FIRST start, so (a) a job that began before the sync window is never fetched and (b) a visit that is only an extra appointment never blocks time. `node scripts/hcp-diagnose.mjs "<name>" <date>` shows which applies to real data. Fix planned after that report: read each job's appointments (and who is dispatched on each), look back far enough to catch jobs already under way, and keep only visits overlapping the window. Cost to weigh: one extra HCP request per job per sync unless the job list already embeds the appointments (the diagnose report says how many it embeds).
- **Estimates and calendar events are not read at all.** In HCP an Estimate (a sales or measuring visit) and an Event (time off, a meeting) are different from a Job, so they never block time here. Possible cause of a tech looking free; the diagnose report flags it when it finds no job for that person and day.

- **Archived jobs.** HCP archives finished jobs (hides them). For an archived job, `GET /jobs/{id}/appointments` and `GET /jobs/{id}` answer `400 {"error":{"message":"Archived job"}}`, while the job LIST still returns it and (as far as the sample showed) does not mark it. Handled so far: the diagnose report flags and skips archived jobs instead of failing, and the look-back skips finished jobs; for live updates an archived job is treated as gone so its booking clears. Not known yet: whether an archived job can sit in the FORWARD window and look falsely booked in the console; the report prints any "archive" field the list carries so we can see.
- **Diagnose a day that is still ahead.** Past days are over (and mostly archived); to test why a tech looks free, run the report for today or a future day where HCP shows a job.
